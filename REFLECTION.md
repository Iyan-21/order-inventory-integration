# Reflection (Lab 3)


**1. PO-103951 (BuyerRef "RO-4") ended with StatusCode 90, which is not in the documentation. How did you work out what it means, and what does your system now do with the stock that will never arrive?**

My tracking job first saw code 90 on PO-103951 and my mapper had no entry for it, so it was stored as UNKNOWN. The order never moved on to 20, 30 or 40 in later polls, and the self-check page counted it under "Noticed a cancelled order", so I concluded that 90 means LegacySupply cancelled it and the goods will never arrive. I did not guess "shipped" or "delivered", because restocking from a wrong guess would put stock in Inventory that does not exist. The mapper now turns 90 into CANCELLED, the order stops being polled, and no stock is added. The job publishes a `SupplierOrderCancelledEvent`, which writes a notice to the activity feed, and places one replacement order for the same units with a new BuyerRef and X-Request-Id, so Inventory is not left short.

**2. LegacySupply never tells you how long a session lasts. Measure it from your logs, state the number, and explain how your adapter decides when to sign in again.**

From my backend log, the line "LegacySupply rejected the session after **[N] seconds**" shows how long a token lived before LegacySupply answered 401. My adapter does not use a fixed timer. It signs in the first time it needs a token. Whenever any call receives a 401, it throws the token away, signs in again and repeats that call once. Reacting to the 401 is safer than guessing a lifetime, because the lifetime is not documented and can change when the instructor changes service conditions. The self-check page shows [N] sign-ins and [N] requests that hit an expired session, which matches this behaviour.

**3. The catalog reports PackSize and orders report Uom "CS". Using one of your own orders, show the arithmetic from units needed, to the Qty sent, to units received.**

Take RO-3: P100 Wireless Mouse, SupplierSku ZZA-1307, PackSize 24, PO-103950. After the customer order, P100 stock was 2, which is below the threshold of 5, and my rule restocks to a target of 20. Inventory therefore needed 20 - 2 = 18 units. Cases = ceil(18 / 24) = 1, so I sent Qty = 1, because Qty counts cases (Uom "CS"), not units. If I had sent Qty = 18, LegacySupply would have delivered 18 cases, or 432 units. When PO-103950 was delivered, the event carried 1 x 24 = 24 units and Inventory restocked by 24, which is 6 more than the 18 it asked for because I round up to whole cases. These numbers match the `cases = 1` and `units = 24` columns of RO-3 in `supplier_orders`. A second example is RO-2 (P300, PackSize 10): 20 units needed, ceil(20 / 10) = 2 cases, 2 x 10 = 20 units received, no rounding surplus.

# Reflection (Lab 4: Marketplace)

**1. Event evt_5829f656a621bfbc (order TG-SGGLMR) reached your application twice, as seq 8 and seq 9, and you processed it once. Show the code and the stored data that made the second delivery harmless, and explain what would happen if your application restarted between the two.**

Every feed event goes through `ChannelOrderProcessor.handle`, which first calls `store.eventDone(eventId)` and, if the id is already in the `channel_event` table, logs "already processed; ignoring redelivery" and returns. Only after the order was created and the decision was sent does it call `store.markEventDone(eventId)`, which inserts the id into `channel_event` (primary key `event_id`, `ON CONFLICT DO NOTHING`). So when evt_5829f656a621bfbc came back as seq 9, the row written for seq 8 was found and nothing was created, reserved or sent a second time. Because that table lives in Supabase and not in memory, a restart between the two deliveries changes nothing: the new instance reads the same row and ignores seq 9. If the application had died after creating the order but before `markEventDone`, the event would be handled again, but `channel_order` has one row per Tiangge order id (`TG-SGGLMR` maps to one shop order), so the retry finds that row, creates no second order, and only resends the decision if `decision_sent` is still false.

**2. Order TG-YD5UCS was backordered at 07:54:26 and accepted at 08:01:50, after PO-104264 was delivered at 08:00:04. Trace how the delivery reached your Inventory and what then resumed the backordered order.**

At 07:54:26 stock was short and PO-104264 was open, so `ChannelOrderProcessor` created the order as BACKORDERED (reserving nothing), stored a `channel_order` row with decision BACKORDERED, and told Tiangge. `SupplierOrderTrackingJob` polls LegacySupply every 90 seconds and saw PO-104264 reach StatusCode 40 at about 08:00:04, so it set the order to DELIVERED and published a `SupplierOrderDeliveredEvent`. `SupplierDeliveryListener` in Inventory handles that event first (it has the highest `@Order`) and restocks the product by the delivered units. `BackorderResolver.onDelivered` runs after that commit and starts `run()` on another thread, because a plain transaction inside an AFTER_COMMIT listener would join the finished one and never commit. `run()` takes `store.pendingBackorders()`, calls `orderService.fulfilBackorder` for TG-YD5UCS, which reserves the stock and sets the order to CONFIRMED, records the resolution ACCEPTED, and sends it to Tiangge. That is the 08:01:50 acceptance. If the send had failed, the 5-second `tick()` would have retried it because `resolution_sent` was still false.

**3. During your restart test your application was down for about 81 seconds while 2 orders arrived. How did the restarted application find those orders, and how did it avoid handling earlier ones again?**

The feed cursor is stored in the `channel_state` table under `feed_cursor`, and `OrderFeedPoller` moves it forward only after `processor.handle(event)` finished for that event (`store.setCursor(seq)`). When the new instance went live (with a new instance id), the first poll called `client.feed(store.cursor(), 50)`, so Tiangge returned only events after the last one I had finished, and those were the 2 orders that arrived while I was offline. Earlier orders were not re-read, because the cursor was already past them. Even if one came back anyway, `channel_event` would stop it, as in question 1. The cursor is in the database and not in memory, so nothing depended on the process surviving. The poller also drains up to 20 pages per run, so a longer outage would have caught up the same way.
